# AI 智能衣橱 APP — 产品需求文档 PRD V1.0

> **文档性质：** 正式文件级归档版（根据 2026-10-17 对话中的完整 PRD V1.0 整理）。  
> **产品版本：** V1.0 / MVP；**更新时间：** 2026-10-18；**状态：** 需求基线、待开发评审。  
> **重要：** 这不是新的 V2 需求；除结构整理与补足跨文件链接外，仍沿用最初确认的「个人数字衣橱 + 2D 换装 + 规则/AI 搭配」范围。  
> **设计稿：** [UI_UX_V1.0.md](UI_UX_V1.0.md)；**开发计划：** [DEV_TASKS.md](DEV_TASKS.md)。

## 1. 目的、背景和定位

用户拥有多件服装，却可能缺乏快速发现合适搭配的能力；部分工具可以管理服装，但没有直观换装体验；一些推荐平台则倾向于展示尚未拥有的商品。因此，本项目以真实个人衣柜为基础，统一「衣服导入和标签化、智能搭配、2D 人物展示、局部调整与保存」。

**一句话定位：** 一款以用户真实衣橱为数据来源，让用户从指定上衣或下装出发，按喜欢的风格获得搭配建议，并在可交互的 2D 小人上预览的手机 APP。

### 1.1 第一版成功定义

用户能够独立完成以下完整闭环：

`添加自己拥有的服装 → 确认 AI 识别信息 → 选择并锁定一件上衣/下装 → 选择风格 → 推荐已拥有的其他单品 → 2D 小人同步展示 → 只换某一个位置 → 收藏 → 下次一键恢复`

除示例模式外，**推荐仅使用当前用户拥有的服装**。2D 小人只做位置、主要颜色与近似廓形展示，不承诺照片级真实试衣。

### 1.2 目标用户

| 用户 | 特点 | 第一优先需求 |
|---|---|---|
| 日常穿搭困难型 | 衣服有一定数量，但不知道怎么组合 | 固定一件衣服，获得其余搭配 |
| 穿搭兴趣型 | 喜欢探索不同风格 | 风格推荐、换一套、收藏 |
| 个人衣柜管理型 | 衣服较多，记不清已买什么 | 图片导入、分类管理、搜索 |

### 1.3 MVP 范围（P0）

用户登录、个人衣柜、拍照/相册和链接导入、AI 基础标签提取及修正、风格选择、固定单品和整套搭配、2D 人物换装、单品锁定与局部替换、搭配收藏与恢复、基本隐私和数据隔离。

### 1.4 明确不做（V1.0）

3D 虚拟人物与可旋转的服装模型、真实身材/尺码还原、真人 AI 试衣、复杂天气自动推荐、电商直接购买、社区社交、服装完整购物推荐、从零训练专用大模型。上述能力都需要后续产品验证后另行立项。

### 1.5 技术和业务假设（待评审）

- 目标首批用户为中文用户；淘宝/天猫链接作为优先导入来源。
- Flutter 作为移动端候选技术；服务端推荐基于个人衣柜，采用规则 + 排序，支持后期迭代 AI。
- 首版使用一个标准 2D 人体基础模板；服装采用有限的形状模板与颜色映射。
- 图片、商品详情、推荐解释均需有异常处理，不能把 API 未授权平台商品当作自动可获取。
- 正式用户衣柜与示例衣柜必须隔离；示例不能伪装成真实已拥有服装。

## 3. 用户流程

### 3.1 服装导入

`选择导入方式 → 选择图片 / 拍照 / 粘贴 URL → 获取服装图片（失败时手动上传） → 异步 AI 分类/去背景 → 用户校正 → 保存到衣橱 → 可参与搭配`

商品链接是**输入方式**，不构成对任意电商详情数据的获取承诺。没有平台授权或提取失败时，保留来源 URL，让用户上传商品图/截图完成录入。

### 3.2 固定单品搭配

`首页 → 点击上衣/裤子 → 选择自己衣柜中的单品 → 默认锁定 → 选择穿搭风格 → 智能搭配 → 浏览至多三套方案 → 局部更换 → 保存`

### 3.3 整套自动搭配

`首页 → 无锁定单品 → 选择风格 → 生成候选组合 → 查看小人和真实图片 → 收藏或换一套`

### 3.4 收藏恢复

`我的穿搭 → 进入套装 → 穿上这套 → 回到首页同步恢复`。如引用服装被删除，不得虚构替代，必须显示缺失位置。

## 5. 数字衣橱

### 5.1 类别

六个主要类别：上衣、外套、下装、连衣裙、鞋子、帽子。子类别包括 T 恤、衬衫、卫衣、牛仔裤、西裤、半身裙、运动鞋、短靴等，采用可扩展字典配置。

### 5.2 核心属性

`garment_id`、`user_id`、`name`、`category`、`subcategory`、`primary_color`、`secondary_color?`、`pattern?`、`fit?`、`style_tags[]`、`seasons[]`、`original_image`、`processed_image?`、`avatar_asset_mapping?`、`source_type`、`source_url?`、`created_at`、`updated_at`。

名称和主类别必须有有效值；识别结果无法判断时可以人工补充，不能无依据填入「高置信度」标签。一个衣服可以拥有多个风格和季节标签。

### 5.3 衣橱管理

- 按主要类别查看双列服装网格；支持基础搜索。
- 点击卡片进入详情；详情可以编辑、删除或开始搭配。
- 删除时提示受影响收藏；历史穿搭显示缺失单品，而不是静默替换。
- 客户端缓存只供显示；服务端需依据登录用户验证 `garment_id` 的所有权。

### 5.4 空状态

无衣服时显示「添加第一件衣服」；无对应类别时显示明确空态；无结果时不误导用户衣服已删除。

## 6. 服装导入

### 6.1 相册 / 拍照

选择来源 → 裁剪/重选 → 上传 → 异步识别 → 用户确认 → 保存。建议支持 JPG、PNG、WebP；HEIC 可在客户端转换。建议单文件 10MB 上限，超限明确提示压缩。

### 6.2 商品链接

粘贴/分享 URL → 校验来源 → 有权限时读取商品基本信息 → 没有权限或图片失败时允许用户上传截图/图片 → 自动识别 → 用户确认。

不能把绕过授权限制的批量抓取作为主方案。保存 URL 不等于商品全属性都可自动获取。应防范恶意 URL / SSRF 等安全风险。

### 6.3 图片属性识别

至少输出：主类别、子类别、主颜色、风格标签、季节，尽力输出图案和版型。支持调整所有自动字段。若背景复杂或多人多衣，提示裁剪到单件。

### 6.4 导入任务状态

`CREATED`、`UPLOADING`、`PROCESSING`、`NEED_CONFIRMATION`、`COMPLETED`、`FAILED`、`CANCELED`。

上传失败、格式错误、抠图失败、无权限链接、AI 分类失败均不应丢弃已经填写的内容；保留可恢复的导入草稿。

## 7. 推荐引擎

### 7.1 模式

- **固定上衣：** 推荐下装、鞋子、可选外套/帽子。
- **固定下装：** 推荐上衣、鞋子、可选外套/帽子。
- **整套推荐：** 不固定任何单品，仅根据用户的主风格生成组合。

### 7.2 基础套装

- `上衣 + 下装 + 鞋子`，或
- `连衣裙 + 鞋子`。

外套与帽子可选。第一版 `连衣裙` 与普通 `上衣/下装` 互斥，复杂叠穿留待后续版本。

### 7.3 规则管道

候选合法性过滤 → 有界的组合生成 → 风格与颜色等维度评分 → 去重及多样性控制 → 最多 3 套推荐 → 解释文字。

初始权重参考（待实验评审）：风格 30%、颜色 25%、版型 20%、季节 15%、偏好 10%。不应写成固定审美真理，权重可调整。

**硬约束优先于评分：** 单品必须真实存在且属于本人，类别合法，连衣裙互斥规则成立，锁定槽位保持不变；遇到未满足硬约束时，绝不返回虚构方案。

### 7.4 锁定与局部替换

- 用户手动选择核心单品时默认锁定。
- 「换一套」不会覆盖锁定单品。
- 明确执行解锁或确认替换后可以改动已锁定槽位。
- 局部更换只改变目标位置；其余锁定单品不变。
- 若无其他合法候选，保留当前展示并告知用户。

### 7.5 部分结果与异常

衣柜里缺少鞋子时，展示已有的部分搭配并指明缺失类别；不能把没有购买的鞋子显示为已拥有。推荐失败时，原穿搭和图片不能清空。

### 7.6 推荐理由

文字必须引用真实已知标签；不得编造衣服的品牌、面料和花纹。

## 8. 2D 虚拟人物（核心）

- 标准站立正面角色；初期一套模板，不依赖真实身材。
- 支持六个槽位：`top`、`outer`、`bottom`、`dress`、`shoes`、`hat`。
- 类别、主颜色、版型映射到有限的 2D 服装模板；真实服装照片以卡片形式独立展示。
- 点击身体旁的热点或文字按钮，打开对应类别选衣弹层。
- 服装修改后：人物图层、选中单品卡、推荐说明和收藏对象引用必须来自同一个 `CurrentOutfit` 快照。
- 没有适合的服装模板时使用通用模板/占位图，不能阻断搭配。
- 明示「2D 穿搭示意，不代表真实试穿效果」。

### 8.1 状态模型

```text
CurrentOutfit
  styleId: string
  garments: {top?,outer?,bottom?,dress?,shoes?,hat?}
  locked: Set<Slot>
  recommendationId?: string
  dirty: boolean
```

Flutter 验证工程中用 `revision` 表示每次成功状态提交后的快照版本。生产版可在上层额外记录 dirty / sourceRecommendationId。

## 9. 穿搭收藏

完整搭配可保存为收藏，保存当前最终单品 ID、对应槽位、风格、名称和创建时间。收藏可打开、恢复、删除；删除收藏不影响衣服。恢复前验证所有服装是否还在；缺失项保留为空位并提示补充。

同一搭配应避免因重复点击而反复创建相同的收藏项。

## 10. 用户和设置

第一版推荐手机号验证码登录，并提供登录保持、退出、协议、隐私、注销入口。用户可选择偏好风格但不强制上传真人照片或填写身材信息。演示模式与正式账号数据不能混淆。权限按需请求。

## 11. 数据结构和接口概要

### 11.1 表

`users`、`user_preferences`、`garments`、`garment_images`、`import_jobs`、`style_definitions`、`outfits`、`outfit_items`、`recommendation_feedback`、`avatar_asset_mappings`。

`outfits` 与 `garments` 为多对多，通过 `outfit_items` 关联。对象存储保存图片，数据库保存受控图片位置，不建议将图片数据直接塞入业务主表。

### 11.2 主要 API

| 方法 | 路径 | 作用 |
|---|---|---|
| POST | `/v1/auth/login` | 登录 |
| GET | `/v1/users/me` | 当前用户 |
| GET | `/v1/garments` | 服装列表 |
| GET | `/v1/garments/{id}` | 服装详情 |
| PATCH | `/v1/garments/{id}` | 编辑 |
| DELETE | `/v1/garments/{id}` | 删除 |
| POST | `/v1/import-jobs/images` | 提交图片导入 |
| POST | `/v1/import-jobs/links` | 提交链接导入 |
| GET | `/v1/import-jobs/{id}` | 查询异步状态 |
| POST | `/v1/import-jobs/{id}/confirm` | 确认并保存 |
| GET | `/v1/styles` | 风格列表 |
| POST | `/v1/recommendations/outfits` | 生成穿搭 |
| POST | `/v1/recommendations/replacements` | 局部替换 |
| GET/POST | `/v1/outfits` | 收藏列表/创建 |
| GET/DELETE | `/v1/outfits/{id}` | 收藏详情/删除 |

所有接口需有鉴权和一致的错误码，后台必须校验衣服归属，写接口应考虑幂等性。更详细接口契约参见 [INTERFACES_V1.0.md](INTERFACES_V1.0.md)。

## 13. 验收清单（节选）

| 编号 | 场景 | 期望 |
|---|---|---|
| TC-001 | 空衣橱 | 提示先导入，不生成个人虚假方案 |
| TC-002 | 导入上衣图 | 标签可修改后成功保存 |
| TC-003 | URL 无法解析 | 手动上传商品图片可继续 |
| TC-004 | 上衣被锁定后推荐 | 上衣保持不变 |
| TC-005 | 用户只替换裤子 | 只改裤子，其他锁定项不变 |
| TC-006 | 选连衣裙且已锁定上衣 | 显示冲突提示，显式确认后解除 |
| TC-007 | 推荐 1 套 | 不会为凑三套生成不存在的衣服 |
| TC-008 | 2D 资产缺失 | 通用人物模板，真实图片正常 |
| TC-009 | 收藏/恢复 | 应用相同服装 ID 的套装 |
| TC-010 | 删除收藏引用的衣服 | 收藏缺失提示，不擅自替换 |
| TC-011 | 网络/AI 失败 | 保留用户已填写的信息 |
| TC-012 | 越权访问他人单品 | 服务端拒绝 |

**建议内部试用门槛：** 常见服装主类识别准确率目标 ≥ 85%；正常支持格式下图片导入成功率目标 ≥ 98%；具有完整衣柜的测试用户至少 80% 能独立完成「选衣→推荐→局部换衣→收藏」。以上是**设计目标**，不是已验证的产品表现。
